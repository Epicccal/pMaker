# _why_udp_session —— UDP 会话层的设计立场

> 只在质疑 `udp_session` 的形态(零字段、必写、无握手)时读。字段与组合规则见
> `udp_session` 层文档。

## 为什么 UDP 会话要显式声明(而 tcp_session 可省略)

TCP flow 有可省略的先例:`flow.stack` 含 `tcp` 就默认 handshake/fin,`tcp_session`
只是改参数的开关。把这套宽容照搬给 UDP —— 含 `udp` 即默认 UDP 会话 —— 会留下一条
**静默歧义路径**:用户想写「一串 standalone UDP 数据报」进了 `flows`,工具却按会话
展开(交换端点、接 `from` 方向),产出与预期相反方向的包,且**不报错不告警**。

强制 `- udp_session: {}` 把意图显式化:写错了立即硬错(报错还能点名层),写对了
语义无歧义。宽容的历史包袱只留给 TCP,不新增第二种。

## 为什么是零字段

UDP 没有可推导的连接状态:seq/ack 不存在,握手/挥手没有,超时与重传是**应用层**
的事(TFTP 自己管,RTP 自己管),pcap 构造器无从也不该模拟。给 `udp_session` 开
`timeout` / `retransmit` 一类字段,等于假装 UDP 层有这些语义 —— 造出来的是「工具
自己发明的协议」,不是任何真实 UDP 流量。

于是本层唯一职责是**标记**:告诉 flow 展开器「本 flow 是 UDP 会话,`from: dst` 的
消息按端点交换发出」。标记无参数,零字段是诚实的形态;写任何字段(`timeout: 3`)
被未知字段校验硬拒,而非静默忽略 —— 静默忽略会让人以为字段生效了。

## 为什么禁 segment 切段

TCP 的 `segment` 切段依赖流重组:接收端按 seq 把多段拼回完整消息,中间态只是
传输细节。UDP 数据报是**独立成帧**的:把一条 DNS 消息按 mss 切成两个数据报,
每个都单独无法解析,这不是「模拟慢网络」,是产出损坏流量。确需多个数据报,
拆成多条 `message` 并用 `offset_time` 控制间隔 —— 每个 message 恰好一个数据报,
帧完整性由用户自己保证,工具不掺和。

## 为什么流式应用层只告警不硬拒

流式协议层(`http_request` 等)的语义是「字节流的一段」,放进单个数据报没有
帧边界语义 —— HTTP over UDP 不是 DNS 那样的数据报协议,是未定义行为。但「语义
可疑」与「配置非法」是两回事:数据报的 payload 只是字节,把 HTTP 字节放进 UDP
并不产出**撒谎的包**(与 dns-over-TCP 不同,那里缺 2 字节前缀,字节本身就是错的),
只产出「解析端还原不了消息」的包 —— 恰是畸形用例想要的东西。按两套异常模型的
分工,这归软告警(`udp.stream-app-layer`),照常出包、提示复核。

告警的判定方向是**正向清单**(命中 `http_request` 等已知流式层才告警),不是
反向排除:UDP 会话将来要承载更多数据报协议(TFTP、QUIC、RTP……),若按
「不告警清单」排除,每进一个协议就要改一次校验器,且放开之前新层全被误报;
正向清单下新数据报层默认就是放开状态 —— 收紧一件坏事不需要拦住所有事,
代价只是新增流式层时须登记进清单(漏登记只漏一条告警,不误伤)。

DNS over TCP 是另一回事:RFC 1035 §4.2.2 要求 2 字节长度前缀,裸复用 `dns` 层
会静默产出缺前缀的畸形。与其加开关不如先不支持:需要时用 `payload_hex` 手拼
前缀 + 消息字节(前缀长度依赖消息长度,恰好是结构化字段最不擅长的事)。

## 端口切换为什么不支持(FTP TID 式)

TFTP 的并发传输用新 TID(端口)续会话,Quake 式 UDP 游戏也常换源端口。这类
「会话中途换端口」要求 flow 状态机维护端口迁移规则 —— 每种应用协议的迁移时机
都不同,结构化表达不了。FTP 先例已经给出答案:拆成两条 flow + `start_after`
表达接续,端口是每条 flow 的声明值,不引入关联字段。
